# Git 发布工作台 MVP

基于 Django 的内部 Git 发布工作台。工具不替代 Git，也不提供任意命令输入，而是把固定的发布流程、前置检查和操作记录放到 Web 页面中。

## 第一版覆盖的流程

```text
开发分支
  -> 合入验证分支
  -> 验证通过
  -> 选择本次上线内容
  -> 基于发布基线分支创建 release
  -> 合并选中的功能/BUG 分支
  -> 检查 release
  -> 执行仓库根目录 build.sh
  -> 人工生产发布与验证
  -> release 合入发布基线分支
```

生产发布不会由工作台自动执行。工作台只记录构建产物和人工验证状态。

## 本地启动

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver 127.0.0.1:8000
```

打开 `http://127.0.0.1:8000/`，先添加项目配置：

- 本地仓库必须是已经存在的 Git 工作区。
- `remote_url` 通常填写 `origin`，也可以填写完整 Git URL。
- `baseline_branch` 是发布基线分支，默认 `stable`。
- `verification_branch` 是验证分支，默认 `uat`，也可配置为 `sit`、`qa` 等实际名称。
- “启用 SaaS 打包”只控制是否显示独立的 `build.sh` 打包入口，不参与 Release 状态和生产验证判断。

## 固定 Git 操作

页面不接收任意 Git 命令。后端只允许以下动作：

- 创建开发分支：同步发布基线分支、从这里创建分支、推送远程。
- 合入验证分支：同步验证分支、依次合并分支、冲突立即停止、成功后推送。
- 创建 Release：先确认发布基线和验证分支已同步，再从发布基线创建 release，并合并已验证通过的提交。
- 检查 Release：检查工作区、基于提交、分支完整性、冲突标记和分支同步状态。
- 执行 SaaS 打包：作为独立功能进入 release 分支并调用现有构建脚本。
- 合入发布基线：生产验证通过并完成文本二次确认后，合并 release 并推送发布基线分支。

每次 Git 命令、执行结果、stdout 和 stderr 都会写入操作日志。

## 防呆规则

- 工作区存在已跟踪文件修改时，禁止继续 Git 操作。
- 开发分支有未推送提交、本地与远程不一致时，禁止合入。
- 验证合入是幂等的；已经包含当前提交时不会重复 merge，也不会重置原有验证状态。
- 验证通过后如果分支出现新提交，必须重新合入验证分支并重新验证。
- 只有验证通过的提交能进入 Release。
- 同一仓库同时只允许一个未结束 Release。
- 已完成的 Release 可以放弃并标记为 `cancelled`，原分支、产物和日志会保留；再次创建时自动使用 `.2`、`.3` 等新序号。
- 合并冲突时立即停止，不继续后续分支。
- 同一 Release 构建成功后不能重复打包。
- 生产验证和 release 合入发布基线都需要明确二次确认。
- 只允许未跟踪的构建产物存在于构建后检查和合入发布基线阶段，已跟踪修改仍会阻断。

## SaaS 打包约定

工作台固定执行仓库根目录下的 `build.sh`，构建日志按增量轮询显示。构建成功后，会从脚本输出中识别以下扩展名的文件路径：

```text
*.tar.gz
*.tgz
*.zip
```

识别到的路径会记录为 `package_path`。如果现有脚本输出格式不同，只需让脚本打印实际产物路径即可。
